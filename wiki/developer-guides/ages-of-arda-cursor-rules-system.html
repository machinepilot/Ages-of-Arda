Introduction for New Users

What is the Cursor Rules System?

The Cursor Rules System is an intelligent guidance framework that provides real-time development standards and best practices while you work in the Cursor editor. Think of it as having an expert looking over your shoulder as you code, offering advice specific to what you're working on.

Why Use It for Game Development?

Game development involves complex systems that must work together: graphics, AI, physics, user interface, storytelling, and more. The Cursor Rules System helps by:

  1. Automatically loading relevant guidelines based on the file you're editing
  2. Ensuring consistency across the codebase regardless of who's working on it
  3. Reducing cognitive load by providing patterns and solutions for common problems
  4. Improving code quality through standardized approaches
  5. Accelerating onboarding for new team members

How It Works in Simple Terms

When you open a file in Cursor, the system:

  1. Looks at the file path and type
  2. Finds matching rules based on glob patterns
  3. Presents those rules within Cursor
  4. Updates the guidance as you switch between files

For example, when editing an AI behavior file, you'll automatically see AI-specific guidelines, whereas editing a memory management file will show memory allocation best practices instead.

System Overview

The Cursor rules system is an integrated set of guidelines that are automatically applied based on the context of files being edited. Each rule provides specific guidance for developing different aspects of the Ages of Arda game, an Angband variant focused on Tolkien's First Age.

Key Components

  • Metadata-Driven Rules: Each rule file contains metadata in a YAML frontmatter that determines when it applies
  • Context-Aware Activation: Rules are automatically loaded based on file paths and types
  • Hierarchical Organization: Rules are structured in logical categories
  • Priority System: Higher priority rules take precedence when multiple rules apply
  • Related Rules: Rules can explicitly reference other related rules

### How Rules Are Applied

1. When a file is opened, Cursor examines the file path
2. The system matches the path against glob patterns in rule metadata
3. Matching rules are loaded in order of priority (highest first)
4. Related rules are also loaded if referenced

### Rule Priorities Explained

The priority number determines which rules take precedence:

- **1000-900**: Master rules (always loaded)
- **899-700**: Domain rules (language/technology specific)
- **699-500**: Feature rules (feature-specific guidelines)
- **499-300**: Specialized rules (very specific contexts)
- **299-100**: Optional rules (guidelines that may not always apply)

How the Self-Healing System Works

  1. Error Collection

    • The system monitors build logs, static analysis, and runtime errors
    • Errors are cataloged with context (file, line, code snippet)
    • Frequency and patterns are tracked over time

  2. Pattern Analysis

    • Similar errors are clustered by signature
    • Common root causes are identified
    • High-frequency patterns are prioritized

  3. Rule Generation

    • New rule proposals are created for common error patterns
    • Each proposal includes:
      • Description of the issue
      • Code examples showing the problem
      • Recommended solution
      • Implementation examples

  4. Human Review

    • Proposed rules are reviewed by developers
    • Rules can be refined or rejected
    • Approved rules are integrated into the system

  5. Continuous Improvement

    • The system tracks which rules reduce error rates
    • Less effective rules are refined or removed
    • The knowledge base grows more accurate over time

Real-World Example: Implementing an NPC AI System

Let's walk through how the rules system guides development of a new NPC AI system:

1. Planning Phase

First, review relevant rule files:

cursor .cursor/rules/ai/ai-gameplay.mdc
cursor .cursor/rules/ai/multi-agent.mdc
cursor .cursor/rules/game/memory-bank.mdc

From these rules, you learn:

  • NPCs should have fallback behavior when AI is unavailable
  • Agent systems should follow the established communication protocol
  • Memory management for dynamic behaviors needs special attention

2. Implementation

Create the implementation file:

touch src/ai/npc_behavior.c
cursor src/ai/npc_behavior.c

Cursor automatically loads relevant rules because the path contains ai/.

Follow the pattern from the rules:

/**
 * Process NPC behavior using the agent system
 * 
 * @param npc The NPC entity
 * @param game_state Current game state
 * @return bool Success or failure
 */
bool
process_npc_behavior(entity_t *npc, game_state_t *game_state)
{
    agent_context_t *context = NULL;
    behavior_result_t *result = NULL;
    bool success = false;
    
    /* Create agent context */
    context = create_agent_context(npc, game_state);
    if (context == NULL) {
        log_error("Failed to create agent context for NPC %s", npc->name);
        return false;
    }
    
    /* Request behavior from AI system */
    result = ai_generate_behavior(context);
    
    /* Fall back to scripted behavior if AI unavailable */
    if (result == NULL) {
        result = get_scripted_behavior(npc, game_state);
    }
    
    /* Apply behavior result */
    if (result != NULL) {
        success = apply_behavior_result(npc, result);
        free_behavior_result(result);
    }
    
    /* Clean up */
    free_agent_context(context);
    
    return success;
}

3. Testing

Based on rules, you know to test:

  • Normal AI behavior generation
  • Fallback to scripted behavior when AI is unavailable
  • Memory management (leaks, use-after-free)
  • Error handling for edge cases

4. Code Review

During review, Cursor highlights compliance with rules:

  • Memory allocation pattern matches the memory-bank.mdc guidelines
  • Error handling follows recommended patterns
  • AI behavior generation includes the required fallback

5. Integration

When integrating with the main game loop, you reference the angband-variant.mdc rule to ensure proper turn processing:

/**
 * Process all NPCs in the current level
 */
void
process_npcs(game_state_t *state)
{
    for (int i = 0; i < state->current_level->npc_count; i++) {
        entity_t *npc = state->current_level->npcs[i];
        
        /* Skip inactive NPCs */
        if (!npc->is_active) {
            continue;
        }
        
        /* Process behavior */
        process_npc_behavior(npc, state);
    }
}

This process ensures the NPC AI system integrates seamlessly with the existing codebase and follows established patterns.

Rule Composition and Interaction

Layering Example

For a file at src/ai/pathfinding/a_star.c, these rules might apply:

  1. code-style/c-style.mdc (Priority: 800)

    • Provides base formatting and syntax guidelines

  2. game/memory-bank.mdc (Priority: 780)

  3. ai/ai-gameplay.mdc (Priority: 700)

    • Adds AI-specific patterns on top of previous layers

  4. Custom rule for pathfinding (Priority: 650)

    • Adds pathfinding-specific optimizations

Each layer builds on previous layers, with conflicts resolved by priority.

Precedence Resolution

When rules conflict, the rule with higher priority takes precedence:

Rule A (Priority 800): "Use 4-space indentation"
Rule B (Priority 600): "Use 2-space indentation for nested loops"

In this case, Rule A takes precedence due to higher priority.

Rule Specialization

Rules can specialize more general rules:

General rule: "Log all errors with appropriate context"
Specialized rule: "For memory allocation errors, include allocation size and current memory usage"

The specialized rule refines rather than contradicts the general rule.

Performance Optimization

Rules application is optimized through:

Caching

The system remembers which rules apply to previously opened files:

# Pseudocode for rule caching
$cachedRules = @{}

function Get-ApplicableRules($filePath) {
    if ($cachedRules.ContainsKey($filePath)) {
        return $cachedRules[$filePath]
    }
    
    $rules = Find-MatchingRules($filePath)
    $cachedRules[$filePath] = $rules
    return $rules
}

Lazy Loading

Rules are only loaded when needed, not all at once:

function Load-Rule($rulePath) {
    # Only parse the rule file when requested
    if (-not $loadedRules.ContainsKey($rulePath)) {
        $content = Get-Content $rulePath -Raw
        $loadedRules[$rulePath] = Parse-RuleContent($content)
    }
    
    return $loadedRules[$rulePath]
}

Rule Indexing

Fast lookup of applicable rules through indexing:

# Build an index of glob patterns to rules
$globIndex = @{}

Get-ChildItem -Path .cursor/rules -Filter "*.mdc" -Recurse | ForEach-Object {
    $content = Get-Content $_.FullName -Raw
    if ($content -match 'glob:\s*"(.+?)"') {
        $glob = $matches[1]
        if (-not $globIndex.ContainsKey($glob)) {
            $globIndex[$glob] = @()
        }
        $globIndex[$glob] += $_.FullName
    }
}
