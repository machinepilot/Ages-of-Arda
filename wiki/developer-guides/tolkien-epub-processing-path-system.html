Introduction

The Path Configuration System is a core component of the Tolkien ePub Processing Framework that provides standardized path management across all components. This guide explains how the system works and how to use it in your development efforts.

System Overview

The path configuration system solves several key problems:

  • Eliminates hardcoded paths that cause cross-platform issues
  • Provides different path sets for different environments (production, testing, development)
  • Centralizes directory creation to ensure all required directories exist
  • Simplifies test implementation by automatically switching paths
  • Improves code maintainability by removing path management boilerplate

Key Components

The path system consists of these core components:

Environment Enum

Defines the three supported environments:

class Environment(Enum):
    PRODUCTION = "production"
    TEST = "test"
    DEVELOPMENT = "development"

Path Templates

Pre-defined paths for each environment:

PATH_TEMPLATES = {
    Environment.PRODUCTION: {
        "processing": PROJECT_ROOT / "processing",
        "logs": PROJECT_ROOT / "processing" / "logs",
        "temp": PROJECT_ROOT / "processing" / "temp",
        # Additional paths...
    },
    Environment.TEST: {
        "processing": PROJECT_ROOT / "processing",
        "logs": PROJECT_ROOT / "processing" / "test_logs",
        "temp": PROJECT_ROOT / "processing" / "test_temp",
        # Additional paths with test-specific locations...
    },
    # Development paths...
}

Core Functions

The system provides several key functions:

  • set_environment(env): Set the current environment
  • get_path(path_type): Get a path for the current environment
  • create_directories(): Create all directories for the current environment
  • get_log_file_path(component_name): Get log file path for a component
  • resolve_path(path_str, base_type): Resolve relative or absolute paths
  • get_memory_bank_path(age, entity_type): Get specialized memory bank paths

Using the Path System

Basic Path Access

To access paths in your code:

from processing.path_config import get_path

# Get a specific path from the current environment
output_dir = get_path('output')
temp_dir = get_path('temp')

# Use the paths in your code
output_file = output_dir / "my_output.json"
with open(output_file, 'w') as f:
    json.dump(data, f)

Setting Up Logging

For component logging:

import logging
from processing.path_config import get_log_file_path

logging.basicConfig(
    level=logging.INFO,
    format='%(asctime)s - %(name)s - %(levelname)s - %(message)s',
    handlers=[
        logging.FileHandler(get_log_file_path('my_component')),
        logging.StreamHandler()
    ]
)
logger = logging.getLogger('my_component')

Resolving User-Provided Paths

When accepting paths from function arguments:

from processing.path_config import resolve_path

def process_file(input_file, output_dir=None):
    # Resolve input file path relative to the input directory
    input_path = resolve_path(input_file, 'epub_content')
    
    # Use default output directory if none provided
    output_path = resolve_path(output_dir, 'output') if output_dir else get_path('output')
    
    # Process the file...
    processed_data = read_and_process(input_path)
    
    # Write to output
    result_file = output_path / f"{input_path.stem}_processed.json"
    with open(result_file, 'w') as f:
        json.dump(processed_data, f)

Path Configuration in Testing

The path system significantly simplifies testing by providing isolated paths for test data and output.

Setting Up Test Environment

All test modules should start with:

from processing.path_config import set_environment, Environment

# Set test environment at the start
set_environment(Environment.TEST)

Directory Structure in Tests

With the environment set to TEST, the system provides paths that won't interfere with production data:

  • processing/test_logs/: Log files from tests
  • processing/test_temp/: Temporary files during testing
  • processing/test_output/: Output files from tests
  • processing/test_data/: Test data files
  • processing/test_reports/: Test result reports

Example in Test Code

def setUp(self):
    """Set up test environment with temporary directories."""
    # These paths automatically use the test environment paths
    self.test_dir = get_path('temp')
    self.output_dir = get_path('output')
    
    # Create test data
    with open(self.test_dir / "test_data.json", 'w') as f:
        json.dump(test_data, f)

Migrating Existing Code

To migrate existing code to use the path configuration system:

  1. Step 1: Import the path configuration

    from processing.path_config import get_path, resolve_path

  2. Step 2: Replace hardcoded paths

    Before:

    output_dir = "processing/output"
log_file = "processing/logs/my_component.log"

    After:

    output_dir = get_path('output')
log_file = get_log_file_path('my_component')

  3. Step 3: Update logging setup

    Before:

    logging.basicConfig(
    handlers=[logging.FileHandler("processing/logs/my_component.log")]
)

    After:

    logging.basicConfig(
    handlers=[logging.FileHandler(get_log_file_path('my_component'))]
)

  4. Step 4: Set the environment in tests

    from processing.path_config import set_environment, Environment
set_environment(Environment.TEST)

  5. Step 5: Remove manual directory creation

    Before:

    os.makedirs("processing/output", exist_ok=True)
os.makedirs("processing/temp", exist_ok=True)

    After:

    # No code needed - directories are created automatically

Benefits and Best Practices

Key Benefits

  • Consistency: All components use the same paths
  • Cross-platform: Works reliably on Windows, Mac, and Linux
  • Test isolation: Tests won't corrupt production data
  • Centralized configuration: Path changes need to be made in only one place
  • Code reduction: Less boilerplate for path handling

Best Practices

  • Always use get_path() instead of hardcoding paths
  • Use resolve_path() for any user-provided paths
  • Set environment to TEST at the start of all test modules
  • Use get_log_file_path() for component logging
  • When adding new path types, add them to all environments
  • Use pathlib.Path methods for path manipulation (not os.path)

Future Development

Planned enhancements to the path configuration system include:

  • Support for user-defined environment configurations
  • Integration with configuration files
  • Path validation to catch incorrect path usage
  • Path usage statistics to identify opportunities for optimization

Frequently Asked Questions

Why use a centralized path system?

A centralized path system ensures consistency, improves maintainability, and makes it easier to adapt the codebase to different environments and operating systems.

How do I add a new path type?

Add the new path to all environment configurations in PATH_TEMPLATES in path_config.py.

Can I use this for paths outside the processing directory?

Yes, the system can resolve any path relative to the project root. For external paths, use resolve_path() with absolute paths.

How does this work with temporary test directories?

In tests, you can still use tempfile.mkdtemp() for truly temporary directories, but for standard test paths, using the TEST environment provides consistency and automatic cleanup.
