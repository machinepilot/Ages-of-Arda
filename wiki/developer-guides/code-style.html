C Code Style Guidelines

Consistent Code for a Consistent World

Ages of Arda follows specific code style guidelines to ensure consistency, readability, and maintainability across the codebase. These guidelines apply to all C code in the project and are enforced through code reviews and automated tools.

Formatting

Indentation and Spacing

  • Use 4 spaces for indentation, not tabs
  • Maximum line length is 120 characters
  • No trailing whitespace
  • Use a single space after keywords like if, for, while, and switch
  • Use a single space around binary operators (+, -, *, /, etc.)
  • No space between function name and opening parenthesis

Example:

// Good
if (condition) {
    do_something();
}

// Bad
if(condition){
    do_something();
}

Braces

  • Opening braces go on the same line as the statement
  • Closing braces go on their own line
  • Always use braces for control statements, even for single-line bodies

Example:

// Good
if (condition) {
    do_something();
} else {
    do_something_else();
}

// Bad
if (condition) do_something();
else
    do_something_else();

Switch Statements

  • Case labels are indented one level from the switch
  • Case contents are indented one level from the case label
  • Break statements align with the case contents
  • Always include a default case, even if it's just a comment

Example:

switch (value) {
    case 1:
        do_something();
        break;
    
    case 2:
        do_something_else();
        break;
    
    default:
        /* Impossible case */
        assert(0);
        break;
}

Naming Conventions

General Rules

  • Use descriptive names that convey meaning
  • Prefer clarity over brevity
  • Be consistent with existing code

Specific Conventions

Element Convention Example
Functions snake_case calculate_damage()
Variables snake_case player_health
Constants UPPER_SNAKE_CASE MAX_INVENTORY_SIZE
Macros UPPER_SNAKE_CASE DEBUG_PRINT()
Typedefs snake_case_t entity_t
Structs snake_case struct player_stats
Enums snake_case enum damage_type
Enum values UPPER_SNAKE_CASE DAMAGE_FIRE

File Naming

  • Source files: snake_case.c
  • Header files: snake_case.h
  • Test files: snake_case_test.c

Comments and Documentation

General Guidelines

  • Write comments that explain "why", not "what"
  • Keep comments up-to-date with code changes
  • Use complete sentences with proper punctuation
  • Avoid obvious comments that duplicate the code

Function Documentation

All functions should have a documentation comment that includes:

  • Brief description of what the function does
  • Parameters and their purpose
  • Return value and its meaning
  • Error conditions and side effects
  • Any special notes or warnings

Example:

/**
 * Calculates damage dealt to an entity based on attack type and defenses.
 *
 * @param attacker The entity performing the attack
 * @param defender The entity receiving the attack
 * @param attack_type The type of attack being performed
 * @param critical Whether this is a critical hit (1) or not (0)
 *
 * @return The amount of damage to be applied, or -1 on error
 *
 * @note This function does not apply the damage, it only calculates it.
 */
int calculate_damage(entity_t *attacker, entity_t *defender, 
                    enum attack_type attack_type, int critical);

File Headers

Each file should begin with a header comment that includes:

  • Brief description of the file's purpose
  • Copyright notice
  • License information

Example:

/**
 * @file combat.c
 * @brief Combat system implementation for Ages of Arda
 *
 * This file contains the core combat mechanics, including damage calculation,
 * hit resolution, and critical hit determination.
 *
 * Copyright (c) 2023-2024 Ages of Arda Team
 * Licensed under the MIT License
 */

Functions

Function Design

  • Functions should be short and focused on a single task
  • Aim for functions under 50 lines; consider refactoring if longer
  • Minimize the number of parameters (aim for 5 or fewer)
  • Avoid deep nesting of control structures

Function Declarations

  • Include parameter names in declarations
  • Group related parameters
  • For functions with many parameters, place each on its own line

Example:

// For functions with few parameters
void update_entity(entity_t *entity, float delta_time);

// For functions with many parameters
void spawn_entity(
    world_t *world,
    entity_type_t type,
    const char *name,
    int x, 
    int y,
    int level,
    uint32_t flags
);

Types and Structures

Type Definitions

  • Use typedefs for complex types to improve readability
  • Append _t to typedef names
  • Define structs and typedefs in header files

Example:

typedef struct {
    char name[MAX_NAME_LENGTH];
    int health;
    int max_health;
    position_t position;
    inventory_t inventory;
} player_t;

Enumerations

  • Use enums for related constants
  • Prefix enum values with a common prefix
  • Consider using enum classes in C++ code

Example:

enum item_type {
    ITEM_NONE = 0,
    ITEM_WEAPON,
    ITEM_ARMOR,
    ITEM_POTION,
    ITEM_SCROLL,
    ITEM_KEY,
    ITEM_COUNT  /* Always keep this last */
};

Memory Management

Allocation and Deallocation

  • Always check the return value of memory allocation functions
  • Free memory in the reverse order it was allocated
  • Set pointers to NULL after freeing them
  • Use the memory management wrapper functions provided by the engine

Example:

// Preferred approach using our wrappers
entity_t *entity = mem_alloc(sizeof(entity_t));
if (!entity) {
    return ERROR_OUT_OF_MEMORY;
}

// Initialize entity...

// When done
mem_free(entity);
entity = NULL;

Memory Ownership

  • Document memory ownership in function comments
  • Be explicit about who is responsible for freeing memory
  • Use consistent patterns for transferring ownership

Error Handling

Return Codes

  • Use consistent return codes across the codebase
  • Return negative values for errors, zero for success, positive for other results
  • Define error codes in a central header file

Example:

int result = load_map(map_file);
if (result < 0) {
    switch (result) {
        case ERROR_FILE_NOT_FOUND:
            log_error("Map file not found: %s", map_file);
            break;
        
        case ERROR_INVALID_FORMAT:
            log_error("Invalid map format in file: %s", map_file);
            break;
        
        default:
            log_error("Unknown error loading map: %d", result);
            break;
    }
    return result;
}

Assertions

  • Use assertions to catch programming errors, not runtime errors
  • Include descriptive messages in assertions
  • Don't use assertions for error handling in production code

Example:

void damage_entity(entity_t *entity, int amount) {
    assert(entity != NULL && "Entity cannot be NULL");
    assert(amount >= 0 && "Damage amount must be non-negative");
    
    entity->health -= amount;
    if (entity->health < 0) {
        entity->health = 0;
    }
}

Macros and Preprocessor

Macro Guidelines

  • Minimize macro usage; prefer inline functions when possible
  • Always wrap macro parameters in parentheses
  • Use do { ... } while (0) for multi-statement macros
  • Add comments explaining complex macros

Example:

#define MAX(a, b) ((a) > (b) ? (a) : (b))

#define LOG_ERROR(fmt, ...) \
    do { \
        fprintf(stderr, "[ERROR] %s:%d: " fmt "\n", \
                __FILE__, __LINE__, ##__VA_ARGS__); \
    } while (0)

Include Guards

  • Use #ifndef/#define/#endif for include guards
  • Name guards based on the file path to avoid conflicts

Example:

#ifndef AGES_ARDA_COMBAT_H
#define AGES_ARDA_COMBAT_H

/* Header contents */

#endif /* AGES_ARDA_COMBAT_H */

Automated Tools

Cursor Rules System

The Ages of Arda project leverages the Cursor Rules System to automatically enforce these style guidelines within the editor. The system provides real-time guidance based on the file you're editing, helping you follow these standards as you code.

Clang-Format

We use clang-format to automatically format code according to our style guidelines. The configuration is provided in the .clang-format file in the repository root.

To format your code:

clang-format -i path/to/your/file.c

Or use the CMake target:

cmake --build . --target format

Static Analysis

We use several static analysis tools to catch potential issues:

  • Clang Static Analyzer: Detects bugs and logic errors
  • Cppcheck: Finds issues not caught by the compiler
  • Valgrind: Detects memory leaks and other memory issues

Run static analysis with:

cmake --build . --target analyze

Conclusion

Following these guidelines helps maintain a consistent, readable, and maintainable codebase. When in doubt, look at existing code for examples or ask for guidance from other developers.

Remember that these guidelines are meant to help, not hinder. If you have a good reason to deviate from them in a specific case, document your reasoning in the code.

This style guide is based on common C programming practices and adapted for the specific needs of the Ages of Arda project. It may evolve over time as the project grows and new patterns emerge.
